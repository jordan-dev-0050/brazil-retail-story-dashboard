# Codex 省 Token Prompt 指南

## 1. 目的

這份文件是給「已經有專案脈絡，只想快速派工」的下法。
重點不是把需求寫完整，而是用最少字數讓 Codex：

- 知道要做哪一段
- 知道先做事，不先寫規格
- 知道遇到缺口時怎麼處理
- 知道最後要怎麼回報

---

## 2. 最省的四段式

實務上最夠用的是這四段：

1. `做什麼`
2. `怎麼做`
3. `缺規格怎麼辦`
4. `最後怎麼回報`

最短模板：

```text
執行 <計畫代號/步驟>。
直接實作，不先寫 Fxx。
有缺口用最小安全假設完成。
最後列假設、風險，並白話說怎麼看你改了啥。
```

這版已經很夠用。

---

## 3. 你的範例可以再縮

你原本的寫法：

```text
請執行 P03 P1。
直接實作，不要先寫 Fxx 文件。
如果發現規格缺口，請採最小安全假設繼續完成，最後再列出假設與風險。
並在最後白話說我如何直觀看你改了啥。
```

可縮成：

```text
執行 P03 P1。
直接實作，不寫 Fxx。
缺口用最小安全假設補完。
最後列假設/風險，白話講怎麼看改動。
```

如果你跟我已經合作一陣子，甚至可以再縮：

```text
做 P03 P1。
直接做，先別補 Fxx。
缺口最小安全假設。
最後講假設、風險、怎麼看改動。
```

## 4. 常用短模板

### 4.1 直接實作

```text
做 <代號>。
直接實作，不先寫文件。
缺口最小安全假設。
最後列假設/風險，白話講改了啥。
```

### 4.2 只改文件

```text
整理 <主題> 成文件。
直接寫，不先提案。
缺口用最小安全假設補齊。
最後講你新增/修改了哪些段落。
```

### 4.3 先 review

```text
review <範圍>。
先找 bug、風險、回歸，不要先講優點。
最後再補摘要與建議。
```

### 4.4 小修小補

```text
把 <問題> 修掉。
直接改。
不要重構擴大。
最後講改法、風險、怎麼驗。
```

### 4.5 指定只做最小範圍

```text
只做 <範圍>。
不要順手擴修。
缺口最小安全假設。
最後講沒做的邊界。
```

## 5. 哪些字常浪費 Token

下面這些常常可以省：

- `請幫我`
- `麻煩你`
- `先幫我看一下`
- `如果可以的話`
- `我想要你幫我`
- 重複講兩次同一個限制

例如：

```text
請幫我執行 P03 P1，麻煩直接實作，如果可以的話先不要寫 Fxx 文件。
```

可以直接改成：

```text
執行 P03 P1。直接實作，不寫 Fxx。
```

意思幾乎沒少，但 token 會比較省。

---

## 6. 哪些資訊值得保留

真正值得保留的只有這些：

- `任務定位`：`P03 P1`、`修某 bug`、`改某檔`
- `執行模式`：直接實作 / 只分析 / 只 review
- `邊界`：不要先寫 Fxx、不要擴修、不要碰 UI
- `缺口策略`：最小安全假設
- `收尾格式`：列假設、列風險、白話說怎麼驗

如果需求已經寫在 repo 文件裡，就不用在 prompt 再重講一次規格。

## 7. 推薦下法

### 極短版

```text
做 P03 P1。
直接實作，不寫 Fxx。
缺口最小安全假設。
最後列假設/風險，白話講怎麼看改動。
```

### 穩定版

```text
執行 P03 P1。
直接實作，不先寫 Fxx 文件。
如果規格有缺口，採最小安全假設完成。
最後列出假設與風險，並白話說我怎麼快速看你改了什麼。
```

### 強限制版

```text
執行 P03 P1。
直接實作，不寫 Fxx，不先提案。
只做這步，不要擴修。
缺口用最小安全假設補完。
最後列假設/風險，白話講改動與驗法。
```

---

## 8. 想更省時的固定尾句

你可以固定在很多任務後面都加這句：

```text
最後列假設/風險，白話講改動與驗法。
```

這句很省，且能穩定拿到：

- 假設
- 風險
- 改了什麼
- 怎麼檢查

---

## 9. 一句話原則

少講背景，多講：

`做哪段 + 怎麼做 + 不要做什麼 + 最後怎麼回報`

如果 repo 裡已經有 `Pxx` / `Fxx` / 現成文件，直接引用代號通常最省。
